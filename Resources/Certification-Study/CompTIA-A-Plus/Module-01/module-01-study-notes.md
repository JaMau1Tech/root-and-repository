# Module 1 Study Notes

*What Does an IT Specialist Do? — CompTIA A+ Core 1 (220-1201)*

Note: the troubleshooting methodology in this module is not a formal
numbered exam objective per CompTIA's own 220-1201 objectives doc, but
it's tested indirectly and constantly through scenario questions,
especially in the real Domain 5.0 Troubleshooting (28% of the exam).

## 1.1 — The Hero of Problem Solving

### 1.1.1 — Role of an IT Specialist

- Core identity: Problem Solver — responsible for a wide range of
    issues across IT equipment/systems

- Day-to-day is ever-changing, no fixed routine — the job is really
    about having a repeatable process, not knowing every answer

### 1.1.2 — Skills and Abilities

Soft skills: Problem Solving (consistent process every time),
Communication (written AND oral, for different audiences), Organization
(clean workspace = faster tool/part location; also organize your
thoughts before communicating).

- Technical knowledge areas: Hardware, Software (OS + apps),
    Networking, Cloud, Security

- These five areas map roughly onto CompTIA's actual domain structure
    (1.0 Mobile Devices, 2.0 Networking, 3.0 Hardware, 4.0
    Virtualization/Cloud, 5.0 Troubleshooting) — this module previews
    the shape of the whole course

## 1.2 — The Troubleshooting Methodology

### 1.2.1 — Best Practice Methodology

Determine cause, symptoms, and consequences of an issue. Priority and
severity matter — critical systems and the most severe issues get
addressed first. Your employer's internal process always takes priority
over CompTIA's generic steps when they differ.

**The 6-Step CompTIA Troubleshooting Methodology (memorize this order
— high-yield for scenario questions)**

- 1. Identify the problem

- 2. Establish a theory of probable cause (includes 'question the
    obvious')

- 3. Test the theory to determine the cause

- 4. Establish a plan of action and implement the solution

- 5. Verify full system functionality (and implement preventive
    measures)

- 6. Document findings/lessons learned, actions, and outcomes

### 1.2.2 — Identify the Problem

- Gather info from the user: exact error messages? anyone else
    affected? how long has it been occurring? what changed recently?

- 'What changed recently' is often the single most useful question
    — most problems trace back to something that changed

- Perform backups before making changes; if the customer is
    responsible for backups, verify they've actually done it

### 1.2.3 — Establish and Test a Theory

- Physically inspect the system, try to reproduce the problem, check
    documentation, ask other techs, read vendor docs

- If you can't reproduce the problem on demand, you can't be sure
    you actually fixed it later

### 1.2.4 — Question the Obvious

- Never skip the simple stuff — is it turned on? is it plugged in?

- Decide: hardware or software related? Physical or logical issue?

- Test each theory individually to isolate the actual cause —
    changing multiple things at once means you won't know what actually
    fixed it

### 1.2.5 — Establish a New Theory or Escalate

- If the first theory doesn't pan out, form a new one and keep
    testing

- Escalate when the issue is: beyond your skill level, beyond your
    knowledge level, or out of scope per company policy/warranty

- Escalating isn't failure — it's part of the process

### 1.2.6 — Implement a Plan of Action

- Options: repair, replace, or workaround — weigh cost-effectiveness
    of repair vs. replace

- Not every issue must be permanently resolved — a workaround can be
    acceptable if business priorities support it (e.g., a temporary
    restore instead of full replacement if a server is being
    decommissioned soon anyway)

### 1.2.7 — Verify and Document

- Verify: confirm the solution resolves the issue, confirm full system
    functionality, put preventive measures in place

- Document: parts used (cost + point of purchase), steps taken, tools
    used, lessons learned

- Documentation matters because someone (you or a coworker) may hit
    the exact same issue later and want the answer already written down
